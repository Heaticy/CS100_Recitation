运行结果是：inside 是 42，但 outside 还是 10。
为什么没改成功？看上面的图：C 语言的函数参数传递，永远是“按值传递”。调用函数时，只是把 main 里实参 n 的值 10，复印了一份，交给 set_number 里的形参 x。
x 和 n 是两个完全独立的对象。你在函数里把 x 改成 42，只是改了复印件；等函数一返回，形参 x 的生命周期就结束了，而 main 里的原件 n 根本没被碰过。
所以，如果我们想让函数真正修改调用者的那个对象，光传它的“值”是不够的，我们得告诉函数：那个对象住在哪个地址。

### 【P7 | 底部标号 5 / 49 | 把地址传进去，函数才能找到原来的对象】[02:35 - 03:20]（45秒）

怎么把地址传进去呢？看左边的修改版。
调用时，我们写 set_number(&n)，用取地址符 & 拿到 n 的地址；函数的形参写成 int *p，代表 p 是一个指向 int 的指针，用来接收这个地址。
在函数内部，写 *p = 42;，意思就是：顺着 p 里存的地址找过去，把那个位置上的对象改成 42。
注意右边这句红字：C 语言依然是按值传递，只不过这一次，我们复印并传递的“值”，是一个地址。

那反过来呢？有没有可能：指针变量还活着，但它指向的那个对象已经死了？

### 【P9 | 底部标号 7 / 49 | 尝试写一个“构造函数”：create_point】[04:05 - 04:55]（50秒）

假设我们想写一个类似构造函数的 create_point(int x, int y)，在里面创建一个结构体 struct Point point = {x, y};，然后直接 return &point;，把它的地址返回给 main 里的指针 p。

### 【P10 | 底部标号 8 / 49 | 为什么新变量可能“无辜被改”？】[04:55 - 05:50]（55秒）

很多同学在自己电脑上跑刚才那段错误代码时，会发现一个特别诡异的现象：明明改的是 p->x = 99，结果后面打印 new_point.x，居然莫名其妙变成了 99！为什么新变量会无辜躺枪？
看这两张对比图：第一次调用 create_point 时，point 住在一块栈空间里；等函数返回，这块栈空间就被回收了。紧接着 main 创建 new_point 时，底层栈实现很可能会复用刚才那块空间。
此时你再拿着旧地址 p 往里硬写 99，实际上就砸到了新住进来的 new_point 头上。
当然，这只是帮大家理解底层发生了什么，C 标准绝对不保证地址一定这么复用。核心结论就一句话：只要所指对象死了，旧地址就废了；要想让对象在函数返回后继续活着，我们必须使用动态内存分配。

### 【P13 | 底部标号 10 / 49 | 先认识Stack与Heap：一层层调用，与一块块申请】[06:35 - 07:25]（50秒）

在写代码之前，我们先在脑子里建立 Stack（栈）和 Heap（堆）的直观画面。
左边是 Stack：它就像一摞严格按调用顺序叠起来的盘子，每进一层函数调用就压入一层栈帧，函数一返回，最上面这层栈帧就自动弹出，所以局部变量寿命很短，而且栈的总空间通常比较有限。
右边是 Heap：它是一片相对宽裕的池子，里面散落着已分配的块和空闲的块。你需要一块空间，就调 malloc 切一块出来；哪块不用了，就调 free 把它还回去，释放顺序完全不受函数调用顺序的限制。

### 【P14 | 底部标号 11 / 49 | 运行时才知道n，直接写int a[n]可以吗？】[07:25 - 08:05]（40秒）

讲到运行时决定数组大小，肯定有同学会问：我在代码里先 scanf("%d", &n)，然后直接写 int a[n];，编译器好像也没报错呀，这样可以吗？
注意，这种写法叫 VLA（变长数组）。虽然它的长度 n 是在运行时才算出来的，但它依然是一个 automatic 局部对象，通常还是挤在 Stack（栈） 空间里，一离开当前作用域照样销毁，也没法扩容。
更重要的一条铁律请大家务必记住：VLA 不是动态分配，而且我们 CS100 的所有作业和考试，全部禁止使用 VLA！

### 【P15 | 底部标号 12 / 49 | 为什么作业禁用VLA？空间不足时能否处理？】[08:05 - 08:55]（50秒）

为什么课程严禁使用 VLA？对比一下左右两边就明白了。
左边用 malloc：如果空间不够申请失败，malloc 会乖乖返回 NULL。我们可以写 if (a == NULL) 来做错误处理、体面退出。
而右边的 VLA 呢？它是往栈上硬塞。如果用户输入的 n 很大，比如几百万，栈空间瞬间就被撑爆了，没有任何返回 NULL 给你检查的机会，程序直接崩溃（Stack Overflow），甚至会带来严重的安全漏洞。
用下面这句话帮大家记住：“发射中心要建在酒泉，而不是紫禁城。” 大小不可控的大数组，要去宽阔的 Heap 上申请，千万不要塞进空间有限、还要维持函数调用的栈里。

### 【P18 | 底部标号 15 / 49 | 动态分配的四个核心接口】[10:35 - 11:10]（35秒）

有了刚才的体感，我们正式认识一下 <stdlib.h> 里的动态分配四大金刚：
第一个 malloc(size)：申请指定字节数的内存，注意里面的内容是未初始化的；
第二个 calloc(count, size)：按元素个数和单个大小申请数组，并且自动把所有字节清零；
第三个 realloc(p, new_size)：调整已有分配块的大小；
第四个 free(p)：释放内存。
下面我们快速看一眼使用它们时的几个关键细节。

### 【P19 | 底部标号 16 / 49 | sizeof：明确写出要申请的对象类型】[11:10 - 11:55]（45秒）

第一个细节：malloc 的参数到底怎么写？
比如我们要申请 10 个 int 的数组，一定要写成 malloc(10 * sizeof(int))。
看中间的图：10 * sizeof(int) 算出来的是实打实的 10 个 int 格子的总字节数；千万不要手滑多打一颗星，写成 sizeof(int *)！sizeof(int *) 只是下面那个灰框——一个指针变量本身的大小（在 64 位机器上固定是 8 字节）。如果你申请一个很大的结构体，却写成

### 【P22 | 底部标号 19 / 49 | 为什么不能直接p = realloc(p, ...)？】[13:15 - 14:00]（45秒）

那如果 realloc 扩容失败了呢？C 标准规定：如果 realloc 失败，它会返回 NULL，但原来的那块内存并不会被释放，依然有效！
这就决定了，我们绝对不能偷懒直接写 p = realloc(p, ...)。
看右边的图：万一扩容失败返回 NULL，你直接赋给 p，就把 p 里仅存的旧地址给覆盖成了 NULL。结果原来的 Heap 块还占着内存，你手里的钥匙却被自己扔掉了，想 free 都找不到地址，当场造成内存泄漏（Memory leak）。

### 【P28 | 底部标号 24 / 49 | Memory layout：一种典型的程序存储布局】[16:50 - 18:05]（1分15秒）

那这些不同寿命的对象，在内存里到底住在哪儿呢？我们来看这张非常经典的 Memory layout（程序存储布局图）。
大家顺着左边从上往下（也就是从高地址到低地址）看：
最上面是 Stack（栈），存放函数调用栈帧和普通局部变量，随着函数调用向低地址方向增长；
往下一格是 Heap（堆），也就是我们 malloc 动态分配的区域，向高地址方向增长，和 Stack 共享中间这片可用空间；
再往下，.bss 和 .data 合称 Static（静态区），全局变量和 static 变量都住在这里：其中零初始化的放在 .bss，非零初始化的放在 .data；
最下面两层是只读的：.rodata 存放字符串字面量等只读数据，.text 存放编译出来的机器指令。
再看最右侧的大括号：在典型的计算机或嵌入式系统里，上面的 Stack、Heap 和 Static 区在运行时都是可读写的，放在 RAM 里；而下面的 .rodata 和 .text 是只读的，可以放在 ROM 或 Flash 里。在嵌入式系统中，.data 变量的初始值也会保存在 Flash 里，通电启
动时再复制到 RAM，而 .bss 区直接在启动时清零。

第二，看最后一行 const char *p = "hello";：指针变量 p 自己住在栈上，而它指向的 "hello" 字符串字面量住在只读的 .rodata 区，所以绝对不能通过指针去修改字符串字面量的内容。

### 【P30 | 底部标号 26 / 49 | Stack frame：函数返回后发生了什么？】[19:00 - 19:35]（35秒）

本节最后一页，我们再看一眼 Stack frame（栈帧）。当 main 调用 function_b、function_b 再调用 function_c 时，栈帧一层层叠上去；一旦 function_c 返回，它的栈帧就被弹出去了。
哪怕内存里原来的旧字节暂时还没被别人覆盖，那个局部对象在规则上也已经彻底死亡了，不能再回头去摸。

第四节：谁负责free：指针、别名与所有权

### 【P31 | 第四节分节页（无底部标号）】[19:35 - 19:40]（5秒）

最后我们进入第四节：既然动态内存不会自动消失，那到底谁负责 free？又有哪些常见的释放陷阱？

### 【P32 | 底部标号 27 / 49 | free：释放的是分配，不是指针变量】[19:40 - 20:20]（40秒）

第一个陷阱：调用 free(p) 之后，指针变量 p 本身会消失吗？会自动变成 NULL 吗？
都不会！ 看右边的图：
第一步，当你执行 free(p) 时，只是把右边那块 Heap 内存归还给了系统，但左边的指针变量 p 依然活着，而且里面还存着刚才那个旧地址，变成了悬空指针！
只有当你执行第二步 p = NULL;，才真正切断了这根危险的虚线。而且 C 标准保证 free(NULL) 是什么都不做的安全操作，所以释放完顺手置 NULL 是一个很好的习惯。

### 【P33 | 底部标号 28 / 49 | 哪几种地址能传给free？】[20:20 - 21:05]（45秒）

第二个问题：随便什么地址都能塞给 free 吗？
看左边的代码：局部变量的地址 &local 不能 free，全局变量 &global 不能 free，已经 free 过的 p 也不能再 free 一次（那叫 Double free）。
最容易犯迷糊的是第 8 行：我用 malloc 申请了 3 个 int，那我传 free(p + 1)，只退掉后面两个格子行不行？
看右边的图：绝对不行！ 这就像你整租了一套三居室，退房的时候必须把整套房子的主钥匙 p（也就是块首地址）交回去，不能说“我把次卧 p + 1 先退给房东”。传给 free 的，只能是 NULL，或者是 malloc/calloc/realloc 原封不动返回的那个块首指针。

### 【P34 | 底部标号 29 / 49 | 两个指针指向同一块分配：p = NULL后，q安全吗？】[21:05 - 21:50]（45秒）

第三个陷阱：指针别名（Alias）。
看左边的代码：我们申请了一块内存交给 p，然后写了一句 int *q = p;。
注意右边的图：这句赋值只是把地址复印了一份给 q，Heap 里的动态分配块依然只有一块！
当你调用 free(p) 并把 p = NULL 之后，p 是安全了，但 q 并没有自动跟着变成 NULL！q 依然指着那块已经死掉的内存。这时候不管是去读 *q，还是再去调 free(q)，全都是致命错误。
记住右下角这句红字：释放的次数只看 malloc 分配了几次，不看你有几个指针变量。

### 【P35 | 底部标号 30 / 49 | Memory leak：指针没了，堆上的分配还在】[21:50 - 22:25]（35秒）

反过来，如果分配了却没人 free 呢？
看这段代码：函数 f 里用局部指针 p 申请了 100 个 int，既没有在返回前 free(p)，也没有把 p 返回给外面的调用者。
看右边的图：当函数 f 结束时，左边的栈帧销毁了，唯一记着地址的钥匙 p 灰飞烟灭；但右边 Heap 里的 100 个 int 还孤零零地占着内存，直到程序结束都没人能释放它，这就是典型的内存泄漏（Memory leak）。

### 【P36 | 底部标号 31 / 49 | 回看create_point：约定谁负责free】[22:25 - 22:55]（30秒）

所以在写实际工程代码时，每块动态内存都必须有明确的 Ownership（所有权约定）。
比如回看我们的 create_point：函数内部负责 malloc，一旦成功返回指针，就把这块内存的“所有权”转交给了调用者 main；main 接过指针使用完毕后，就必须由 main 负责调用 free(p)。

### 【P37 | 底部标号 32 / 49 | 链表：每个节点都是一次独立分配】[22:55 - 23:25]（30秒）

如果遇到更复杂的结构，比如链表呢？
大家看这个链表图：head 指向第一个节点 20，第一个节点的 next 指向第二个节点 10。
因为每个节点都是当时单独调用一次 malloc 申请出来的，所以当你只写一句 free(head) 时，仅仅释放了第一个节点，后面的节点并不会自动跟着释放！我们必须写一个循环，顺着链表一个节点一个节点地释放。

### 【P38 | 底部标号 33 / 49 | 释放链表：为什么必须先保存next，再free？】[23:25 - 24:10]（45秒）

那怎么写这个释放循环？这里有一个经典的必考细节。
看右上方错误示范：如果你一进循环就先写 free(head)，再去写 head = head->next，那就完蛋了！这就好比你人还在河这头，先把桥给炸断了，再去已释放的节点里读 next，当场触发 Use-after-free。
正确的拆桥姿势看右下方和左边第 3 到 5 行：
第一步，先派一个探路指针 struct Node *next = head->next;，把下一座桥的位置存下来；
第二步，放心大胆地 free(head) 拆掉当前节点；
第三步，head = next;，顺着刚才存好的探路指针走到下一个节点。

### 【P39 | 底部标号 34 / 49 | 内存错误小结：先问哪条规则被破坏了】[24:10 - 24:55]（45秒）

到这里，我们已经把 C 语言里最常见的五类内存错误全部见识过了。大家看这张总结表：
1. Out-of-bounds（越界）：比如申请了 n 个元素却去访问 a[n]；
2. Uninitialized read（未初始化读取）：局部 int local; 没赋值、或者 malloc 刚拿出来没写值就直接读；
3. Dangling / Use-after-free：返回局部变量 &point，或者链表先 free(head) 再读 next；
4. Double free（重复释放）：两个别名指针 p 和 q 指向同一块内存，free(p) 之后又调了一次 free(q)；
5. Memory leak（内存泄漏）：函数结束没释放，或者 p = realloc(p, ...) 失败把原地址覆盖丢了。
写作业遇到前面几类崩溃时，强烈建议大家开启上节课讲过的 AddressSanitizer，一抓一个准。

### 【P40 | 底部标号 35 / 49 | 带走这四个问题】[24:55 - 25:35]（40秒）

最后，今天下课请大家带走这四个灵魂拷问：
第一，在哪里？ 分清指针变量自己和它指向的对象，分别住在哪个区域；
第二，活多久？ 分清作用域（Scope）和三种生命周期（栈上局部、静态区、堆上动态分配）；
第三，能访问吗？ 动用指针前，先查有没有初始化、有没有越界、是不是 NULL、所指对象还活着吗；
第四，谁释放？ 每一次 malloc 都要有对应的 free，哪怕在错误退出的分支上也别忘了清理。
记住底下这句话：地址还在，不代表对象还在；函数返回，也不代表动态对象被释放。
